# 写一份 AI 岗位简历

用求职者提供的旧简历、项目笔记和目标 JD 起草正文。默认跟随用户的语言。用自然中文写完整的句子，保留团队实际使用的技术名词。Agent 无法打开参考文件时，可以直接按本页写作。

## 整份简历怎么排

- **页首**：姓名、目标岗位、联系方式和教育信息。把「作品链接」放在页首 GitHub 旁，优先直达招聘方可公开查看的代表作，例如产品演示、开源仓库或公开文章。只有作品链接时，也放在页首。只使用用户提供的公开地址。一项有代表性的开源贡献、论文或奖项也可以放在这里。
- **正文**：有正式工作经历时，可以先写工作。以实习为主要经历时，直接从实习写起。公司或团队、岗位和起止时间放在同一行，下面列项目。兼职、独立项目和开源贡献按实际身份归类。
- **项目**：标题先写读者能识别的项目名。必要时在标题后补一句它是什么。每个项目都按下文写成四行 STAR。

从零起草时，用已确认的事实写齐有内容的栏目。重排旧稿时，先把相关项目往前放、合并重复内容、删空栏目。只要求调整结构时，保留原句，必要时补衔接。详见 [简历结构](references/resume-structure.md)。

## 把个人亮点放在最前面

起草或重组整份简历时，如果用户还没说过最想突出的能力，先问：「你觉得自己最值得招聘方记住的一点是什么？哪段经历、成果或作品最能证明它？」可以先整理已有素材。用户要求直接出稿时，从已确认的事实里选一个亮点，并在稿外说明这是暂定写法。

把用户认可的亮点、反复做得好的事和目标岗位放在一起看，选一个最有证据的交集。优先用目标 JD 判断相关性；需要引用当下趋势时，查近期可信来源，或者请用户提供具体岗位。把趋势用在取舍上，文案写候选人确实做过的事。编辑单个项目时，沿用已经明确的亮点。

把亮点放在姓名正下方、正文之前，写成一句具体的陈述。可用个人动作、已交付的成果或可打开的作品来支撑。下面的一句话自我介绍负责交代经历、作品与下一步方向，避免再重复亮点的整句话。

## 一句话自我介绍

在页首的 GitHub 和作品链接下面写一句话，依次交代过去在哪段工作或实习中做过什么、一项可公开核验的代表作、现在想探索或发展的方向。代表作名称可直接链接到作品。方向有变化时，可以用半句说明是什么经历或问题让你想往这个方向走。当前已经在做的事和今后希望做的事，用相应的动词写清楚。没有用户确认的方向或动机时，起草已有部分并在稿外询问。见[中英文示例](references/resume-structure.md#一句话自我介绍)。

## 每个项目都写四行

- **背景（S）**：先说谁在做什么，再说卡在哪里。若读者不了解项目，先交代它解决的实际问题。
- **我的职责（T）**：写自己负责并完成了哪项工作、交付了什么。只有素材确认时，才写「项目负责人」「独立实现」或「主导」。参与团队工作时，把本人负责的模块写具体。
- **行动（A）**：按实际工作顺序写。可以从输入、关键处理到输出，也可以先写遇到的难点，再说明如何处理。重点项目按模块写出两三项关键实现，作为「行动」下的子项。说明输入、处理、输出和影响交付的关键取舍。用了某项技术时，写清它在方案里解决什么问题。每个模块都应能看出本人做了什么。
- **结果（R）**：写已上线的功能、实际使用、实验证据或可核对的指标。比较前后变化时保留基线、单位和已知范围。区分离线、试点和线上，注明团队结果的归属。

Markdown 和 HTML 各用四项列表，LaTeX 用四个 `item`。英文用 **Background / My responsibilities / Action / Result**。一页简历可以缩短每项。每个项目只展示一组 STAR。见[项目示例](references/examples.md)和[英文写法](references/workflow.en.md)。

## 写清重点项目的工作场景和技术方案

- 项目放在真实的公司或团队、岗位和时间下。单独改写一段项目时，可在标题上方补这行出处，便于直接放回简历。开源、个人和课程项目按实际身份标注。
- 「我的职责」点出本人负责的环节和交付边界。「行动」展开和岗位最相关的实现细节，说明流程怎么走、组件如何配合、异常怎么处理。做过对照实验或方案选型时，可以写清为什么这样选。
- 「结果」对应项目实际交付或可核对的数据。材料只写了技术名或一句职责时，先用已知内容起草，再追问关键设计细节。公司、参数、架构和成果以素材为准。

## 选材与表达

- 看目标岗位要交付什么，再选能证明这些能力的项目。同一段经历投不同岗位，可以突出不同模块，保留原有事实、技术和指标口径。只有 JD 时，围绕该岗位的工作提出最多三个取材问题。见 [AI 岗位参考](references/ai-roles.md)。
- 写清动作和对象。比如「实现意图路由，按任务选择查数工具」比「负责智能化能力建设」更容易理解。技术流程要能读出各步骤的关系。版本对比只在能说明为什么改、本人负责什么时保留。
- 素材没给出数字时，写实际交付、验收或复测发现。只做完原型或离线验证时，写明做到哪一步。素材对不上时，正文先用已确认的事实，把待补信息留在稿外。

## 按 BOSS 直聘 JD 改简历和写打招呼语

用户提供 BOSS 直聘职位链接、截图或 JD 正文时，按 [BOSS 直聘投递写法](references/boss-application.md)处理，英文稿可用 [English application guide](references/boss-application.en.md)。用该岗位的实际职责挑选和改写经历，每个项目仍保留「背景、我的职责、行动、结果」。用户同时要简历和打招呼语时，先给简历正文，再给一条可直接复制的打招呼语。用户只要其中一项时，只交付该项。

## 给关键经历留出核验途径

- **作品**：优先附能直接打开的产品页、演示、代码仓库或本人提交的 PR。页首放代表作，具体项目旁可附各自的链接。链接应能让读者看到作品或个人贡献。
- **工作和实习**：写清公司、岗位、时间和本人职责。用户希望提供背调联系人时，可以另备一份私下发送的联系人名单。经对方同意后，注明姓名、职务、与你的工作关系及工作邮箱或公司电话，按招聘方要求提供。
- **指标和成果**：保留已有的基线、测量范围和归属。内部记录可以留作本人核对。公开简历只放获准公开的材料。

## 交付

用户要简历时，先给可以直接复制的正文。检查每个项目是否按顺序写了背景、我的职责、行动和结果，能否看出本人职责，数字和归属是否一致。最多附三个会影响成稿的待确认问题。公开稿里只使用获准公开的指标、标识和链接。

用户需要 LaTeX 或 PDF 时，可用[黑白单栏 LaTeX 模板](templates/resume.tex)，保留清晰的标题层级和字号。用户只要求论文式排版时，按同样的版式处理现有文档。

英文稿可参考[英文工作流](references/workflow.en.md)。双语稿使用同一组事实，两版的职责、数据和验证范围须一致。
